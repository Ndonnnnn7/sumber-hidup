# PRD implementation notes

The original `PRD.Md` is the baseline, with one explicit scope change requested by the client: the admin page, login, and management APIs are removed. This supersedes section 6.6 and the related no-code management requirement/user story US-06. Catalog content is maintained through server data files. The updated visual direction follows the user's colorful stationery reference while retaining the PRD's clean retail layout, generous whitespace, organized catalog, clear calls to action, responsiveness, and accessible contrast. The original PRD itself has not been changed.

The palette uses PRD navy `#2B4C7E`, orange `#E8552E`, mustard `#F4A340`, paper white `#FAF7F2`, and charcoal `#2D2D2D`. Pink, blue, green, and purple add variety across categories, banners, contact, and favorites. Orange buttons use a darker shade `#BD3C1D` so their white labels remain readable. Category colors consistently identify planner (pink), notebooks (blue), office supplies (green), and writing tools (yellow); labels remain explicit so navigation never depends on color alone. New categories fall back to purple. Shared tokens are in `src/styles.css`, with the component palette in `src/theme.css`.

The hero photograph now shows colorful stationery on a light wooden desk. Product photos and specifications retain their original colors. The established typography and page structure are retained for this color update: Inter is self-hosted; the serif wordmark uses self-hosted Cormorant Garamond. Lucide supplies interface icons.

| PRD requirement          | Implementation                                                                                                                                                                     |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 6.1 Homepage             | Hero, editable categories, featured/new product flags, values, company introduction, catalog/contact CTAs                                                                          |
| 6.2 Catalog              | Search, category, subcategory, stock and price filters; popular/new/price sorting; pagination; shareable filter URLs                                                               |

| 6.4 About                | Brand introduction, purpose, values, institutional partnership CTA; historical claims await confirmed company data                                                                 |
| 6.5 Contact              | Visitor email form saved privately on the server, SMTP notification when a sender is configured, provided WhatsApp number, phone, optional public email/address/map/hours          |
| 6.6 Management           | Removed at the client's request; products, categories, prices/stock, and hero/store settings are edited in server data files                                                       |
| 6.7 SEO/performance      | Per-page metadata, server-rendered product titles/descriptions, sitemap, robots, clean URLs, lazy loading, compressed local WebP                                                   |
| Responsive/accessibility | 375/768/1024/1440px layouts, semantic elements, labeled forms, skip link, visible focus, native modal focus handling and Escape, reduced-motion support, automated contrast checks |
| Security                 | No management API or web inbox; private inquiry storage; origin checks; server-side contact validation; rate limiting; honeypot; Helmet                                            |

Additional convenience: device-local saved products with a combined WhatsApp inquiry. This is a favorites list, not a shopping cart; Phase 2 payments, accounts, POS sync and order tracking are not included.

The nine products and their prices/specifications are editable sample content. Product photography is generated. The phone/WhatsApp number is user-supplied. Missing contact details and historical statistics are not fabricated. Empty store details are omitted, with WhatsApp links for location/hours instead. Entering an address enables a Google Maps embed.

Catalog data and contact submissions persist as JSON on one Node server. This requires a persistent disk and backup policy; multi-instance hosting would require migration to a shared database. SMTP notifications target the supplied address once sender credentials are configured. Each inquiry records its email status; failed or unconfigured delivery is disclosed on the contact page with a WhatsApp fallback. The server operator can review contact submissions in the private `inquiries` array of `data/store.json`; there is no public API for reading messages. See the README for SMTP setup and manual content updates. HTTPS termination, the final domain, real inventory, and confirmed business details are deployment/content handoff items.
